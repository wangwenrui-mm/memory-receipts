# 架构说明

## 一句话

把"记得住"和"说得清"拆成两层：**记忆层负责存**，**核验层负责判**。两者之间靠"来源标记"连接。

```
            ┌─────────────────────────────────────┐
   输入 ───▶│ bridge.handle(text, user_id)        │
            │  · 装配上下文（九层，硬上限）        │
            │  · 调模型                           │
            │  · 剥离控制块                       │
            │  · 写回记忆（带来源标记）            │
            └──────────────┬──────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   记忆层              核验层              人格层
   （九层）          （claim_audit）      （persona）
```

---

## 一、九层记忆

每一层都有硬上限，所以**上下文总量恒定**（约 6k token），不会越聊越贵。

| 层 | 存什么 | 上限 | 作用 |
| --- | --- | --- | --- |
| 置顶 | 他明确要求"要记住"的事 | 条数上限 | 永不遗忘 |
| 灵魂 | 她的自我描述 | 字数上限 | 人格一致性 |
| 信件 | 双方写的长信 | 最近 N 封 | 情感锚点 |
| 共享 | 他说的、要"说给她听"的话 | 最近 N 条 | 单向留言 |
| 日记 | 每天一篇 | 最近 N 篇 | 时间连续性 |
| 摘要 | 长期对话的压缩 | 字数上限 | 代替原始历史 |
| 事实/瞬间 | 结构化记忆 | 条数上限 | 精确回忆 |
| 向量+SQLite | 语义检索 | 按查询取 top-k | 捞旧事 |
| 归档 | 全量流水 | 只读 | 审计 |

**为什么这样设计**：把所有记忆都塞进上下文，成本会随对话轮数线性上涨，几周后就不可用了。分层 + 硬上限让成本保持常数。

---

## 二、来源归因

每条记忆带来源标记：

| 标记 | 含义 | 能不能当证据 |
| --- | --- | --- |
| 原话 | 他实际说过的 | ✅ |
| 概括 | 系统对原话的压缩 | ⚠️ 可引用，但不算原证据 |
| 推断 | 系统自己的推测 | ❌ |
| 回复 | 系统自己生成的 | ❌ |

**这是整个系统的地基**：核验时必须能回答"这条信息是谁说的"。

## 三、核验流程（claim_audit）

```
陈述 → 抽取（参数 + 数值 + 单位） → 检索证据 → 判定 → 标记
```

### 判定结果只有五种

| 结果 | 含义 |
| --- | --- |
| 有依据 | 证据里能找到匹配记录 |
| 已过时 | 记录存在，但已被更晚的结果覆盖 |
| 矛盾 | 记录存在，数值对不上 |
| 未溯源 | 记录里没有，或单位不在词表 |
| 计划 | 识别为规划/目标，不做核验 |

### 三个关键规则

**① 证据集合排除自指**

检索时跳过所有 `来源 = 回复/推断` 的记录。

理由见 README：否则判定器会用"她自己否认过"证明"事实不存在"，把真实记忆误判成虚构。

**② 只标记，不改写**

判定结果不影响原始记录，只在装配上下文时加标记：

```
原始：他昨晚很生气（事实）
标记：他昨晚很生气【已被否定的主张】
```

**③ 时效判定要显式声明**

记录可以带 `date` / `scope` / `superseded_by`：

- 同参数 + 同 scope + 更晚日期 → 旧的判"已过时"
- **未声明 scope → 一律视为有效**（宁可两条都有效让人复核，也不静默丢弃真实数据）

这条是刻意保守的：不同批次的实验数据都可能是真的。

## 四、人格层

`data/persona.json` 里的六维参数：

| 维度 | 影响 |
| --- | --- |
| 黏人 | 主动消息频率、回复长度 |
| 毒舌 | 用词尖锐程度 |
| 话量 | 回复长度上限 |
| 独立 | 是否表达不同意见 |
| 敏感 | 对语气变化的反应 |
| 主动 | 主动发起话题的频率 |

另外有 `bond`（关系温度）、`trust`（信任）、`disappoint`（失望）。

**变化是缓慢的**：每次对话只微调，避免一句话就性格大变。这样长周期看有"成长感"。

## 五、离线任务

两个不依赖对话的后台任务：

| 任务 | 频率 | 作用 |
| --- | --- | --- |
| `offline_diary.py` | 每天 21:45 | 写日记（读当天的对话 + 共享留言） |
| `offline_growth.py` | 每周 | 微调人格参数 |

**为什么要离线**：如果没有对话就不写日记，人一忙起来她就会"失忆几天"。离线任务保证时间连续性。

## 六、通道抽象

`Bridge.handle(text, user_id)` 与通道无关。QQ 只出现在发送函数里：

| 方法 | QQ 通道 | 控制台通道 | 网页通道 |
| --- | --- | --- | --- |
| `send_text` | 发 QQ 消息 | print | 存到 `_last_reply`，由 HTTP 返回 |
| `send_bubbles` | 拆成多条发 | 直接 print | 拼接 |
| `send_sticker` | 发表情包 | 打印"表情包" | 忽略 |
| `call` | 调 OneBot 接口 | 拦截 | 拦截 |

**加新通道 = 继承 Bridge + 重写这几个方法**，核心逻辑一行不用改。

## 七、数据流（一轮对话）

```
1. 收到文本
2. 取出该用户的对话历史（带 TTL）
3. 装配 system 上下文
   ├─ 置顶 / 灵魂 / 信件 / 共享 / 日记 / 摘要 / 事实
   ├─ 向量检索 top-k（按当前输入）
   └─ 时间、心情、六维
4. 调模型
5. 剥离控制块（[[自改]][[提议]] 等给程序看的块）
6. 发送
7. 写回：历史（带 TTL）+ 长期记忆（带来源标记）
8. 若触发条件满足 → 核验该轮陈述
```

## 八、成本控制

| 手段 | 效果 |
| --- | --- |
| 九层硬上限 | 上下文恒定，不随轮数上涨 |
| 摘要代替原始历史 | 同样的信息，更少的 token |
| 选择性核验 | 只有含数值/时间指代的句子才核验 |
| 向量检索 top-k | 只捞相关旧事，不全量塞入 |
| `--mock` 模式 | 调试零成本 |

实测：普通对话约 ¥0.002–0.006/轮，日记约 ¥0.004/篇。
